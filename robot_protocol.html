로봇 통신 프로토콜

UI/서비스(RobotClient)가 버전 있는 실행 시퀀스를 제출하고 단계 상태를 조회하는 방식을 설명합니다. 요청·응답 모두 한 줄짜리 JSON이며, 코드 기준은 robot_client.py입니다.

개요

  • 전송 방식: 재사용 가능한 TCP 소켓에서 요청·응답을 한 번에 하나씩 처리하는 line-based 프로토콜입니다. 요청과 응답은 각각 JSON 한 줄입니다.
  • 줄바꿈: 소켓은 newline="\r\n"으로 열립니다. 클라이언트가 보내는 \n은 전송 시 \r\n으로 변환되고, 응답도 \r\n으로 끝나야 readline()이 한 줄로 인식합니다.
  • 연결 주체: 로봇이 TCP 서버, RobotClient가 클라이언트입니다. connect()는 ip/port/timeout_ms 설정이 이전과 동일하면 기존 연결을 재사용하고, 다르면 재연결합니다.
  • 설정 위치: config/settings.yaml의 robot.ip, robot.port, robot.timeout_ms, robot.mock_enabled.
요청 직렬화: 응답을 못 받거나(OS 오류, 빈 응답, JSON 파싱 실패) ack가 기대와 다르면 RobotClientError를 던집니다. OS 오류·빈 응답인 경우 소켓을 즉시 닫고, 다음 호출 시 자동 재연결합니다.
Legacy: 기존 REQ_JOB과 SET_PACK_POSE는 호환성 용도로만 남아 있으며 deprecated입니다. 새 연동은 반드시 시퀀스 명령을 사용합니다.
목업: robot.mock_enabled=true이면 TCP를 열지 않습니다. 동일한 상태 응답 계약으로 기본 3초마다 step을 진행시키므로, 실제 로봇 서버 없이 UI·시퀀스 통합을 검증할 수 있습니다.

요청 / 응답 흐름

클라이언트는 응답의 cmd가 요청과 같고 status가 "ACK"일 때만 성공으로 처리합니다. 그렇지 않으면 RobotClientError를 던집니다.

공통 메시지 envelope

방향필드의미
요청cmd명령 이름. SUBMIT_SEQUENCE 또는 GET_SEQUENCE_STATUS.
payload명령별 데이터를 담는 dict. 새 필드(예: move_type)는 여기 추가합니다.
응답cmd요청의 cmd를 그대로 echo.
status성공 시 "ACK". 그 외 값(예: "ERROR")이나 누락 시 실패로 처리됩니다.

연결 관리

메서드동작
connect(config)동일 설정으로 이미 연결돼 있으면 재사용, 다르면 기존 연결을 끊고 새로 연결.
reconnect(config)무조건 끊고 다시 연결.
disconnect()stream/socket을 닫고 상태 초기화. 실패해도 예외를 올리지 않고 로그만 남김.
connected소켓이 열려 있는지(프로퍼티). 실제 로봇 쪽 연결 상태를 보장하지는 않음.

명령: SUBMIT_SEQUENCE

submit_sequence(config, sequence) — 피킹·임시 적치·패킹의 순서와 release pose를 한 번에 전달합니다. destination.approach_pose는 생성·저장·전송하지 않습니다. 비주문 blocker의 임시 적치 release_pose는 고정 설정값이 아니라, 현재 PCD에서 자동 검출한 평평한 지지면의 빈 공간을 blocker별로 분리해 계산한 값입니다.

요청 예시

{"cmd":"SUBMIT_SEQUENCE","payload":{"sequence":{"schema_version":"1.0","job_id":"run-1","frame":{"name":"robot_base","distance_unit":"mm","angle_unit":"deg","robot":"doosan"},"status":"ready","steps":[{"step_no":1,"object":{"segment_id":"s-blocker","segment_index":2,"task_id":null,"product_id":null,"product_name":"검출 상품 S2"},"pick":{"robot_pose":[100,200,300,0,180,0],"base_to_flange":[],"confidence":0.91},"stacking":{"status":"on_top_of","blocks":["s-target"]},"purpose":"clear_blocker_to_temporary","destination":{"type":"temporary","release_pose":[420,180,125,0,180,0],"support_plane":{"point_mm":[0,0,100],"normal":[0,0,1]}},"depends_on":[]},{"step_no":2,"object":{"segment_id":"s-target","segment_index":1,"task_id":"task-1","product_id":"product-1","product_name":"주문 상품"},"pick":{"robot_pose":[110,205,250,0,180,0],"base_to_flange":[],"confidence":0.94},"stacking":{"status":"underneath","blocks":[]},"purpose":"pack_order","destination":{"type":"packing","release_pose":[600,0,200,0,180,0]},"depends_on":[1]}],"blocked_reasons":[]}}}

응답 예시

{"cmd": "SUBMIT_SEQUENCE", "status": "ACK", "payload": {"job_id": "run-1", "status": "queued"}}
payload 필드타입설명
sequencedictschema_version, job_id, frame, status, steps, blocked_reasons를 포함한 실행 계획.

실행 시퀀스 계약

필드의미
sequence.statusready인 경우에만 제출합니다. blocked이면 클라이언트와 GUI가 전송을 거부하며, blocked_reasons만 보고합니다.
step_no / depends_on1부터 시작하는 실행 번호와 선행 완료 step 번호입니다. 로봇은 의존 step이 성공한 뒤 후속 step을 수행해야 합니다.
purposepack_order는 주문 상품 패킹, clear_blocker_to_temporary는 비주문 blocker 임시 적치입니다.
pick.robot_pose선택 로봇 profile의 피킹 TCP pose입니다. 함께 제공되는 base_to_flange는 진단·통합 검증용 변환입니다.
destinationtype: packing은 release_pose만, type: temporary는 release_pose와 계산 근거인 support_plane을 포함합니다. 두 형태 모두 approach_pose는 없습니다.

명령: GET_SEQUENCE_STATUS

get_sequence_status(config, job_id) — 현재 단계와 전체 실행 상태를 조회합니다.

요청 예시

{"cmd": "GET_SEQUENCE_STATUS", "payload": {"job_id": "run-1"}}

응답 예시

{"cmd": "GET_SEQUENCE_STATUS", "status": "ACK", "payload": {"job_id": "run-1", "status": "running", "current_step": 2, "completed_steps": 1, "total_steps": 3}}
payload 필드타입설명
job_idstring제출 ACK에서 받은 작업 식별자. 응답은 status, current_step, completed_steps, total_steps, failure_reason, step_statuses를 반환.

오류 처리

상황동작
TCP 연결 실패 (connect 중 OSError)연결을 정리하고 RobotClientError("로봇 연결 실패 (ip:port): ...").
전송/수신 중 OSError소켓을 닫고 RobotClientError("로봇 통신 실패: ...").
응답이 빈 문자열 (상대가 연결 종료)소켓을 닫고 RobotClientError("로봇으로부터 응답을 받지 못했습니다 (연결 종료).").
응답이 JSON으로 파싱되지 않음RobotClientError("로봇 응답을 JSON으로 해석할 수 없습니다: ..."). 연결은 유지됨.
응답의 cmd 불일치 또는 status != "ACK"RobotClientError("예상한 ack와 다른 응답을 받았습니다: ..."). 연결은 유지됨.
JSON 파싱 실패나 ack 불일치는 연결 자체는 끊지 않습니다. 다음 요청은 같은 연결을 그대로 재사용하려 시도합니다.

nc로 로봇 서버 흉내 내어 테스트하기

로컬에서 로봇 서버 없이 TCP 프로토콜을 확인하려면 config/settings.yaml의 robot.ip/robot.port(기본 127.0.0.1:5001)를 그대로 두고, 그 포트를 nc로 열어 요청을 받고 JSON ack를 입력합니다. GUI 동작만 확인하려면 nc보다 목업 로봇을 사용하세요.

1회성 테스트

nc -l 5001

요청 JSON 한 줄이 화면에 찍히면 ack JSON을 입력한 뒤 Enter 대신 Ctrl+D(EOF)로 마무리합니다. EOF로 연결이 끊겨도 readline()은 버퍼에 있던 내용을 그대로 반환하므로 \r\n 없이 한 번은 정상 동작합니다.

  • SUBMIT_SEQUENCE 요청 → {"cmd": "SUBMIT_SEQUENCE", "status": "ACK"}
  • GET_SEQUENCE_STATUS 요청 → {"cmd": "GET_SEQUENCE_STATUS", "status": "ACK"}

연결을 유지하며 여러 번 주고받기

nc -lk 5001

ack JSON을 입력한 뒤 Ctrl+V Ctrl+M(리터럴 \r 삽입) → Enter로 ...\r\n을 그대로 전송하면 연결을 유지한 채 다음 요청도 같은 세션에서 받을 수 있습니다. -k는 클라이언트 연결이 끊겨도 계속 리스닝하는 옵션입니다.
